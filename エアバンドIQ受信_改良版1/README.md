# 1号機 改良版1（rtl_tcp ＋ チャンネル登録・高速スキャン）

運用中の 1号機のファームウェア（`エアバンドIQ受信/`、rtl_tcp）はそのまま残し、**別のビルドとして**作った改良版です。
同じソースから `-DFASTSCAN=1` でビルドし、ビルドフォルダも `firmware/build_fastscan1/`（1号機用）・`firmware/build_fastscan2/`（2号機で試す用）に分けています。

## できること

- **rtl_tcp（GQRX）はこれまでどおり**使えます（TCP 1234、設定も同じ）。GQRX が接続している間はスキャンを止めてチューナーを GQRX に渡し、切断するとスキャンに戻ります
- GQRX がつながっていない間は、**登録したチャンネルをボード上で高速スキャン**し、信号があれば AM 復調した音声を LAN（UDP）で Mac に送ります
- チャンネルは **名前・個別スケルチ・一時スキップ（SKIP）** 付きで最大 256 件登録、フラッシュに保存（`SAVE`）
- 受信の記録: HIT / END をその場で表示（時刻付きで `~/fastscan_log.txt` に保存）、`LOG` で直近 64 件
- `TUNE 118.1` で 1 チャンネルを聞き続ける（スケルチ付き）、`TUNE OFF` でスキャンに戻る
- 2号機のスキャナーと同じ連携（UDP 1238）で、複数台が同じ局を取り合わない（番号の小さい機が優先）

## 速くした仕組み（2号機のスキャナーとの違い）

| | 2号機 実験機（scanner.c） | 改良版1（fastscan.c） |
|------|------|------|
| 窓の切替 | 毎回 R820T を再同調（I2C 書き込み＋PLL ロック待ち） | 近い窓（`SPAN` 1.8 MHz 以内）どうしは **RTL2832U の DDC だけ**動かす（USB 制御転送 1〜2 回、I2C・PLL 待ちなし）。チューナーの IF フィルタを約 2.3 MHz に広げてある |
| 切替後の待ち | 転送の終わりを待ってから切替、3 ms 分を捨てる | 転送を打ち切り、切替後にドングルの FIFO を空にするので、届くデータは全部新しい窓のもの（捨てる量 0） |
| USB 転送 | 1024 B（2 ms 分） | 512 B（1 ms 分）。GQRX 接続中は従来どおり 4096 B |
| ノイズでの空振り | 1 回のノイズで HOLD（3 秒）止まる | 受信に入った直後に 8 ms 平均で確かめ、確認できなければ 40 ms で次へ（HIT も出さない） |
| 1 チャンネルだけの窓 | 窓の中心がそのチャンネルに重なり、AM の搬送波が DC 除去で消える（十数 dB 弱く見える） | 中心を 12 kHz ずらす |
| 音声 | 20 点平均で 12.5 kHz（隣のチャンネルは約 -18 dB） | 2 段フィルタ（4 kHz まで平坦、隣のチャンネルは -74 dB 以下）。スケルチが閉じたら音声を止める（HOLD 中の雑音なし） |

PC 上のシミュレーション（切替時間は仮定値: チューナー 4 ms、DDC 0.4 ms、FIFO クリア 0.5 ms）で、エアバンド 26 チャンネル（21 窓）の 1 巡が
SPAN 0（毎回チューナー切替）160 ms → **SPAN 1800 で 98 ms、SPAN 4000 で 83 ms**。実機の値はログの `win/s` と `STAT` の `one pass` で確認してください。

※ 2号機の scanner.c にも「1 チャンネルだけの窓」の問題が残っています（このフォルダの作業では 2号機のコードは変更していません）。

## 書き込み（まず 2号機で試す）

1号機はそのまま運用し、2号機（10.5.2.21）に入れて確かめてから 1号機に入れる手順です。

**2号機に書き込む**（初回は cmake から自動で行います）

    sh ~/rp2350-poe-airband-iq/host/ota_fastscan.sh 2

書き込み後は PoE を抜き差ししてください（ドングルのリセットのため）。

**チャンネル登録**（例のファイルを編集してから流し込む。2号機は 10.5.2.21）

    nc 10.5.2.21 1237 < ~/rp2350-poe-airband-iq/host/fastscan_channels_example.txt

**音声を聞く**（要 `brew install ffmpeg`。10 秒ごとにボードへ HELLO を送り、音声の送り先をこの Mac にします）

    sh ~/rp2350-poe-airband-iq/host/fastscan_listen.sh 2

**操作画面**（コマンドを打てる。HIT / END を時刻付きで表示し `~/fastscan_log.txt` に保存）

    sh ~/rp2350-poe-airband-iq/host/fastscan_console.sh 2

**速さの確認**（5 秒ごと）

    nc 10.5.2.21 1236 | grep --line-buffered -E "fscan|\[stat\]"

`[fscan] measure  win/s 213  ch/s 263  hop: ddc 900 us, tuner 4900 us (72/s) ...` のように出ます。

**問題なければ 1号機へ**

    sh ~/rp2350-poe-airband-iq/host/ota_fastscan.sh 1

1号機では番号を付けない `fastscan_listen.sh` / `fastscan_console.sh` がそのまま使えます（既定が 1号機）。GQRX とデスクトップの「エアバンド受信」アプリはこれまでどおりです。

## 元に戻す

**1号機を確認済みの rtl_tcp に戻す**

    python3 ~/rp2350-poe-airband-iq/host/ota_push.py 10.5.2.20 ~/rp2350-poe-airband-iq/エアバンドIQ受信/board1_rtltcp_2029ad0.bin

**2号機をスキャナー実験機に戻す**

    sh ~/rp2350-poe-airband-iq/host/ota2.sh

設定の保存場所が別（改良版1 はフラッシュ 0x3E0000、2号機スキャナーは 0x3F0000）なので、行き来しても互いの登録は消えません。

## ポート

| ポート | 用途 |
|------|------|
| TCP 1234 | rtl_tcp（GQRX）。接続中はスキャン休止 |
| TCP 1235 | OTA |
| TCP 1236 | ログ |
| TCP 1237 | 設定・受信記録（`HELP`） |
| UDP 1238 | 複数台連携（2号機スキャナーと同じ `MON` / `END`） |
| UDP 1240+号機 | 音声（12500 Hz、16bit、モノラル）。1号機 = 1241 |

## コマンド（TCP 1237）

| コマンド | 内容 |
|------|------|
| `ADD 118.100 TWR -50` | 登録（名前・スケルチは省略可、順不同。スケルチは `-` か `+` で始まる数字）。登録済みなら名前・スケルチだけ変更 |
| `DEL 118.1` / `CLEAR` | 削除 / 全削除 |
| `SKIP 118.1` / `UNSKIP 118.1` | 登録したまま一時的に飛ばす / 戻す |
| `LIST` | 設定と全チャンネル（直近レベル `last`、雑音の底 `floor`、受信回数 `hits`） |
| `STAT` | 設定と速さ（`one pass` = 1 巡の時間） |
| `LOG` | 直近 64 件の受信（何分前、長さ、最大レベル） |
| `SQL -53` | 全体のスケルチ（dBFS） |
| `SNR 8` | 雑音の底（floor）より 8 dB 以上も条件にする（0 = 使わない） |
| `HOLD 3000` | 信号が消えてからその局で待つ時間（ms） |
| `GAIN 40.2` / `GAIN AUTO` | チューナーゲイン |
| `PPM 0` | 周波数補正 |
| `TUNE 118.1` / `TUNE OFF` | 1 チャンネルを聞き続ける / スキャンに戻る |
| `SCAN ON` / `SCAN OFF` | スキャンの開始 / 停止 |
| `AUDIO AUTO` / `AUDIO 10.5.2.10` / `AUDIO OFF` | 音声の送り先（AUTO = HELLO を送った Mac、なければ最後に 1237 に接続した Mac） |
| `WATCH ON` / `WATCH OFF` | この接続に HIT / END を流す / 止める |
| `SAVE` | フラッシュに保存（電源を切っても残る） |
| `QUIT` | 接続を閉じる（ファイルを流し込むときの最後に） |

調整用: `SPAN <kHz>`（0 = 毎回チューナー切替、200〜4000）、`SETTLE <us>`（DDC 切替後に捨てる時間、既定 0）、`TSETTLE <us>`（チューナー切替後、既定 1000）、`PLLWAIT <us>`（既定 2000）、`NAVG <1-8>`（1 窓の FFT 回数、既定 2）、`BW <Hz>`（1 チャンネルの幅、既定 6000）、`XFER <bytes>`（スキャン中の USB 転送、既定 512）

## LED

| 色 | 意味 |
|------|------|
| 緑 | GQRX（rtl_tcp）接続中 |
| 水色 | スキャンで受信中（または TUNE 中） |
| 青 | スキャン中 / 待ち受け |
| 赤・白・紫・黄 | 1号機と同じ（USB 未検出・初期化中・チューナーエラー・LAN なし） |

## 調整のヒント

- **ヒットしない / 空振りが多い**: `LIST` の `floor`（雑音の底）を見て、`SQL` を floor より 6〜10 dB 上に。チャンネルごとに `ADD 118.1 -48` のように個別でも決められます。`SNR 8` にすると floor 基準も加わります
- `STAT` の `unconfirmed` は、ノイズで入りかけて確認で落とした回数です。多すぎる（1 秒に何回も）なら SQL を少し上げると速くなります
- **SPAN**: 大きいほどチューナーの切替が減って速くなりますが、IF フィルタの端に来るチャンネルは数 dB 弱く見えることがあります。2 MHz を超えるとチューナーのフィルタが 6 MHz 幅に切り替わります
- `fail` が増える（PLL がロックしない）なら `PLLWAIT 3000`
- 直前の窓の強い信号が混ざって見えるときは `SETTLE 250`
- ずっと出ている局（ATIS など）は `SKIP` で飛ばす

## 実機で確かめてほしい点

このファームウェアはビルドと、PC 上でのスキャン処理のシミュレーション（信号検出・受信・音声・コマンド・保存）までは確認済みですが、実機ではまだ動かしていません。

1. **DDC だけの切替で正しい周波数を測れているか**: 常に出ている局（または手持ちの無線機）を登録し、`SPAN 1800` と `SPAN 0` の両方で同じチャンネルが HIT し、`LIST` の `last` がほぼ同じになること。おかしければ `SPAN 0` にすれば 2号機と同じ切替方式（チューナーを毎回再同調）で動きます
2. **USB が安定しているか**: `[stat]` の `usberr` と `[fscan]` の `fail` が増え続けないこと
3. **GQRX との切替**: GQRX を起動すると LED が緑になり、終了すると青に戻ってスキャンが再開すること

## 電波法について

受信は自由ですが、特定の相手方に対する通信（管制交信など）の内容を他人に漏らしたり利用したりすることは、電波法第59条で禁止されています。
